# Agent 任务看板 PRD

版本 v0.2 · 2026-10-24 · 部署平台：Cloudflare（Workers + D1）

## 1. 背景与目标

多个 BOT 与人协同工作时，任务靠口头或聊天分派，容易冲突、遗漏、无记录。目标：做一个在线任务看板，任务**提前规划、定向派发**，不做争抢；所有人可见全部任务；BOT 只执行派给自己的任务；全程自动留痕。

## 2. 角色

| 角色 | 说明 | 权限 |
| --- | --- | --- |
| 管理员（人） | 规划并发布任务、改派、催办 | 发布、改派、查看全部 |
| BOT | 执行者，通过 MCP/CLI 接入 | 查看全部；仅可认领、操作派给自己的任务 |
| 观察者（人） | 监督 | 只读 |
| 验收 BOT | 按项目绑定，既是该项目任务的发布人，也是验收人 | 发布、验收本项目任务（不能验收自己执行的任务）；查看全部 |

## 3. 核心流程

1. 管理员或项目验收 BOT 发布任务，指定执行 BOT 和时限（默认 1 小时），状态为「待领取」
2. 被指派的 BOT 认领，状态变「进行中」
3. BOT 完成后提交结果与报告，状态变「待验收」；无法完成则提交原因，状态变「未解决」
4. 时限内 BOT 必须提交结果；超过时限仍未提交，系统自动转为「未解决」（原因：超时未提交结果）并标黄，由管理员决定重派或改派

验收环节：

- BOT 提交后，由该项目的验收 BOT 验收（成功 / 失败）
- 验收成功：任务结束
- 验收失败：系统自动汇总（原任务 + 上轮结果 + 失败原因），以该验收 BOT 名义发布新任务，默认派给原执行 BOT，轮次 +1，重新计时
- 默认最多 3 轮（含首次）；达到上限仍失败，转「需人工处理」，交管理员

## 4. 功能需求

### 4.1 发布任务（P0）

- 填写：任务内容（必填）、指派给（必填，下拉选已登记 BOT）、时限（默认 1 小时；可选 30 分钟 / 1 小时 / 2 小时 / 4 小时 / 8 小时 / 12 小时 / 24 小时）
- 系统自动记录：发布人、发布时间、截止时间；初始状态固定「待领取」
- 管理员可发布任何项目的任务；验收 BOT 只能发布本项目的任务

### 4.2 看板展示（P0）

- 表格列：# / 项目 / 任务 / 指派给 / 状态 / 轮次 / 发布人 / 发布时间 / 完成时间 / 结果 / 验收
- 顶部统计：全部、进行中、待验收、验收成功、超时、未解决、需人工处理
- 按状态、按 BOT 筛选；超时行标黄
- 所有人可见所有任务

* 前端模板（与本 PRD 一致，含验收操作与各状态示例）：https://claude.ai/artifact/L2ijYfS63AjHZEYcBpdMp9
* 待验收的任务行内提供「验收成功 / 验收失败」操作，失败须填原因；验收失败后自动出现下一轮任务；第 3 轮仍失败则显示「需人工处理」

### 4.3 认领与执行（P0）

- BOT 只能认领 assignee 等于自己的任务，服务端强制校验，否则拒绝
- 认领时系统记录领取时间

### 4.4 完成与报告（P0）

- 完成时间：BOT 提交「完成」后，系统记录收到的时间，BOT 不可自填；每个任务无论成败，时限内都必须提交结果
- 结果：由执行 BOT 在完成时提交一句话摘要
- 报告：BOT 同时提交报告，命名 `BOT名-日期-序号.md`
- 未解决：由执行 BOT 提交原因

### 4.5 超时处理（P0）

- 超过截止时间仍未提交结果，系统自动将状态转为「未解决」，原因记为「超时未提交结果」，并标黄
- 管理员可将其重新放回待领取，或改派给其他 BOT

### 4.6 验收与循环（P0）

- BOT 提交后状态为「待验收」，只有该项目的验收 BOT 可验收；验收 BOT 不能验收自己执行的任务
- 验收结果：成功 / 失败（失败须填原因）
- 验收失败：系统自动汇总（原任务 + 上轮结果 + 失败原因），以该验收 BOT 名义发布新任务，默认派给原执行 BOT，轮次 +1，重新计时
- 最大轮次默认 3（含首次），可按任务修改；达到上限仍失败，转「需人工处理」，交管理员

### 4.7 改派（P1）

- 管理员可修改 assignee，保留改派记录

### 4.8 项目登记与路由（登记表 P0，自动配对 P2）

- 项目登记表：项目 ↔ 验收 BOT（同时是发布人）↔ 执行 BOT；验收 BOT 发布任务时选项目，系统自动配对执行 BOT
- 未匹配进「未分配」区；支持主责+备份

## 5. 状态机

`待领取 → 进行中 → 待验收 → 验收成功 / 验收失败（→ 新一轮待领取，最多 3 轮，用尽转「需人工处理」）；进行中 → 未解决`；`超时`不是独立状态，只是看板上的标黄标记；超过时限仍未提交结果时，系统自动转为「未解决」（原因：超时未提交结果），管理员可将其重新放回待领取或改派。

### 5.1 状态一览与验收示例

| 状态 | 含义 | 谁触发 | 下一步 |
| --- | --- | --- | --- |
| 待领取 | 已发布，等待被指派 BOT 认领 | 发布人 | 进行中 |
| 进行中 | BOT 已认领 | 执行 BOT | 待验收 / 未解决 |
| 待验收 | BOT 已提交结果与报告 | 执行 BOT | 验收成功 / 验收失败 |
| 验收成功 | 终态，结案 | 验收 BOT | 无 |
| 验收失败 | 本轮不合格，自动发布下一轮 | 验收 BOT | 新一轮「待领取」 |
| 未解决 | BOT 报告失败，或超时未提交结果（系统自动转入） | 执行 BOT / 系统 | 管理员重新放回待领取或改派 |
| 需人工处理 | 达到最大轮次（3）仍验收失败，不再自动发布 | 系统 | 管理员审批 |

验收示例（均已在前端模板中展示）：

- 示例 1：第 1 轮验收成功，直接结案（#51）
- 示例 2：第 1、2 轮验收失败，第 3 轮验收成功，结案（#41 → #42 → #43）
- 示例 3：连续 3 轮验收失败，转「需人工处理」，等待审批（#31 → #32 → #33）
- 示例 4：执行 BOT 超时未提交结果，自动转「未解决」并标黄（#65）
- 示例 5：待验收任务，可当场点击验收成功 / 失败体验循环（#61、#62）

每次验收失败，系统自动生成的新任务包含：原任务 + 上轮结果 + 失败原因，由该项目验收 BOT 发布，默认派给原执行 BOT。

## 6. 字段与责任人

| 字段 | 填写方 |
| --- | --- |
| 任务内容、指派给、时限 | 管理员 |
| 发布人、发布时间、截止时间 | 系统 |
| 领取时间 | 系统（BOT 认领时） |
| 完成时间 | 系统（BOT 提交完成时） |
| 结果、报告 | 执行 BOT |
| 未解决原因 | 执行 BOT |
| 验收结果、验收原因 | 验收 BOT |
| 轮次、验收时间 | 系统（最大轮次默认 3） |

## 7. 接口设计：一套服务，三种入口

核心是一套 HTTP API，MCP 与 CLI 都是它的封装，保证三者行为一致。

### 7.1 HTTP API

| 方法 | 路径 | 说明 | 调用方 |
| --- | --- | --- | --- |
| POST | /api/tasks | 发布任务 | 管理员 |
| GET | /api/tasks | 查询任务（可按 assignee/status 过滤） | 所有人 |
| POST | /api/tasks/:id/claim | 认领 | 被指派 BOT |
| POST | /api/tasks/:id/complete | 完成（结果+报告） | 被指派 BOT |
| POST | /api/tasks/:id/fail | 未解决（原因） | 被指派 BOT |
| POST | /api/tasks/:id/reassign | 改派 | 管理员 |
| POST | /api/tasks/:id/accept | 验收（result + note） | 本项目验收 BOT |

发布示例：`{ "title": "导出本月消课流水表", "assignee": "数据BOT", "deadline_minutes": 120 }`，成功返回 201。

### 7.2 MCP 接口

- 在 Worker 上提供远程 MCP 服务，使用 Streamable HTTP，路径 `/mcp`
- 工具与 HTTP API 一一对应：`list_tasks`、`claim_task`、`complete_task`、`fail_task`、`publish_task`（管理员 / 验收 BOT 可用）、accept\_task（仅验收 BOT 可用）
- 适用于 Claude Code、Codex、OpenCode 等支持 MCP 的 BOT

### 7.3 CLI

- 对 HTTP API 的命令行封装，例如 `board list`、`board claim 21`、`board done 21 --result "已修复" --report ./x.md`
- 适用于不支持 MCP 的 BOT 或脚本

### 7.4 三端接口对应表

要求：所有 HTTP 接口都必须有对应的 MCP 工具和 CLI 命令，参数、行为、错误码一致，三端共用同一套服务端校验。

| 功能 | HTTP | MCP 工具 | CLI 命令 |
| --- | --- | --- | --- |
| 发布任务 | POST /api/tasks | publish\_task | board publish |
| 查询任务 | GET /api/tasks | list\_tasks | board list |
| 认领 | POST /api/tasks/:id/claim | claim\_task | board claim \<id> |
| 完成 | POST /api/tasks/:id/complete | complete\_task | board done \<id> --result --report |
| 未解决 | POST /api/tasks/:id/fail | fail\_task | board fail \<id> --reason |
| 验收 | POST /api/tasks/:id/accept | accept\_task | board accept \<id> --pass 或 --fail --note |
| 改派 | POST /api/tasks/:id/reassign | reassign\_task | board reassign \<id> --to |
| 查询项目 | GET /api/projects | list\_projects | board projects |
| 登记项目 | POST /api/projects | register\_project | board project add |

## 8. 鉴权

- 每个 BOT 一个独立令牌，服务端凭令牌识别身份
- 管理员使用独立管理令牌；验收 BOT 同样一个独立令牌，只能发布、验收本项目的任务
- 「只能操作自己的任务」必须在服务端校验，不依赖 BOT 自觉

## 9. 数据模型

`tasks`：id、title、assignee、status、publisher、created\_at、claimed\_at、deadline\_at、done\_at、result、report\_path、project、parent\_id（上一轮任务）、round（第几轮）、max\_rounds（默认 3）、accept\_result、accept\_note、accepted\_by、accepted\_at

`bots`：id、name、token\_hash、role（执行 BOT / 验收 BOT）

`projects`：id、name、acceptor\_bot（验收 BOT，也是发布人）、executor\_bots

## 10. 技术方案

- 后端：Cloudflare Worker；数据库：D1；前端：Worker 返回的单页 HTML
- 报告文件存储：R2（或写入 D1 文本字段，首版可简化）

## 11. 验收标准

1. 管理员可发布任务，发布人、时间自动记录
2. BOT 认领他人任务时被拒绝
3. 完成时间由服务端写入，BOT 无法伪造
4. 超时任务自动转为「未解决」并标黄
5. 同一任务通过 HTTP、MCP、CLI 三种方式操作结果一致

验收新增标准：

- 执行 BOT 提交后任务进入「待验收」，只有本项目验收 BOT 能验收，且不能验收自己执行的任务
- 验收失败自动发布新一轮任务，内容含原任务、上轮结果、失败原因
- 达到最大轮次（默认 3）仍失败，转「需人工处理」，不再自动发布

## 12. 里程碑

1. M1：D1 表 + 发布/查询/认领/完成/验收接口 + 鉴权 + 项目登记表

3. M3：MCP 与 CLI
4. M4：改派、自动路由
