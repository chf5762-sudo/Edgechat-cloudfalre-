# Agent 任务看板 验收方案

版本 v1.0 · 2026-10-24 · 依据：PRD v0.4、前端 v2（Agent\_任务看板\_v2.html）· 冲突时以前端为准

## 1 目的与通过标准

本方案把 PRD 的每个编号（U 页面信息、B 按钮、S 静态流转、D 动态流转、P 三端一致）拆成**可直接执行的用例**：写明前置条件、操作步骤、预期结果。执行者（人或 Agent）按用例逐条执行并记录结果，全部通过即验收合格。

**通过标准（缺一不可）：**

1. REQUIRED 清单中的每个编号都至少有一条用例执行过，且结果为 PASS（覆盖率 100%）。
2. 严重、高级缺陷为 0；一般缺陷必须有修复计划并经确认。
3. 同一动作在 HTTP / MCP / CLI 三端结果和错误码一致。
4. 每条用例有证据（截图或接口响应），失败用例附复现步骤。
5. 「已知差异」（见第 11 章）逐条有结论，不混入缺陷统计。

## 2 环境、身份与执行约定

### 2.1 测试身份

| 身份 | 角色 | 所属 / 说明 |
| --- | --- | --- |
| 管理员 | admin | 全部权限 |
| 排课验收BOT | acceptor | 排课系统验收人（也是该项目发布人） |
| 写码BOT、测试BOT | executor | 排课系统执行 BOT（顺序：写码、测试） |
| 数据验收BOT | acceptor | 数据报表验收人 |
| 数据BOT、报表BOT | executor | 数据报表执行 BOT |
| 文档验收BOT | acceptor | 文档库验收人 |
| 文档BOT、写作BOT | executor | 文档库执行 BOT |
| 观察者 | observer | 只读 |

### 2.2 两套环境

| 环境 | 身份切换方式 | 数据 | 适用 |
| --- | --- | --- | --- |
| 演示（前端内置后端） | 页面「当前身份」下拉 | 浏览器内存，刷新即重置 | 页面、按钮、文案、交互验收 |
| 正式（Cloudflare Worker） | 令牌输入框「登录」「退出」 | D1 / R2 | 全部用例，含并发、三端、安全、限流 |

标记说明：用例末尾的【演】= 演示环境可执行；【正】= 仅正式环境；未标记两者都执行。

### 2.3 测试数据准备

- 图片样本：PNG（<300KB）、PNG（>300KB 且长边>2000px）、JPEG、WebP、GIF、伪装成 .png 的 SVG、6MB 图片、10 张图片的集合。
- 文本样本：200 字 / 201 字标题；1000 / 1001 字验收标准；500 / 501 字原因；5000 / 5001 字报告；含 `<script>`、`<img onerror>` 的文本；含 `http://`、`https://`、`javascript:` 链接的文本；以 `= + - @` 开头的文本。
- 每个用例使用**独立任务**，不依赖其他用例的执行顺序和结果。
- 造状态的捷径：待领取（发布）→ 进行中（认领）→ 待验收（完成）→ 未解决（报告失败）→ 需人工处理（连续 3 轮验收失败）→ 已关闭 / 验收成功 / 验收失败。超时用 TEST\_MODE 的「⏱模拟超时」或 `deadline_seconds`。

### 2.4 执行约定（给执行验收的 Agent）

1. 严格按编号顺序执行；每条用例结果只能是 **PASS / FAIL / BLOCKED**，不得跳过。
2. 写操作后先看界面提示，再用接口响应或刷新后的列表二次确认，两者必须一致。
3. 预期里出现的文案**逐字**比对，不做近似判断。
4. FAIL 后继续执行其余用例，最后统一汇总；BLOCKED 必须写明阻塞原因和解除条件。
5. 状态变化类用例，除界面外还要检查详情时间线里新增的事件（操作人、动作、前后状态、说明）。
6. 被拒绝的请求（403 / 409）必须同时检查：任务状态未变、时间线**没有**新增事件。
7. 每完成一章，在第 10 章覆盖矩阵里勾选对应编号。

### 3.5 状态说明区（U-50）

页面底部逐字核对 10 行，一字不差：

1. `状态说明（黄色行 = 超时；橙色行 = 待验收或待领取超过 24 小时，仅提醒）`
2. `待领取：已发布，被指派 BOT 尚未认领　|　进行中：BOT 已认领，时限从认领时开始计算`
3. `待验收：BOT 已提交结果，等待本项目验收 BOT 验收　|　验收成功：终态，结案`
4. `验收失败：自动汇总并发布下一轮任务，轮次 +1，验收标准和图片一并带入下一轮`
5. `未解决：BOT 报告失败，或超时未提交结果（系统自动转入）；管理员可放回待领取或改派`
6. `需人工处理：达到最大轮次（3）仍验收失败，管理员三选一：再开一轮（轮次重置）/ 改派 / 关闭`
7. `已关闭：管理员终止任务（终态）；管理员可在详情里强制关闭未结束的任务，或为进行中的任务延期`
8. `放回待领取 / 改派 / 再开一轮 / 关闭 / 强制关闭 / 延期需填写原因，记入时间线，不可撤销`
9. `图片：Ctrl+V 粘贴、拖拽或点「📎 图片」选择；PNG / JPEG / WebP / GIF，单张 ≤5MB，每次最多 9 张`
10. `时间均为北京时间（UTC+8），非当天显示「月-日 时:分」；页面每 5 秒自动刷新`

## 5 按钮验收（B）

通用要求（对每个按钮都检查）：① 仅对 `my_actions` 允许的身份显示；② 请求期间按钮置灰，防止重复提交；③ 成功后列表、统计、详情自动刷新；④ 服务端对无权限返回 403，状态不符返回 409；⑤ 每次成功操作在时间线新增一条事件，被拒绝的请求不新增事件。

## 6 静态流转验收（S-01 \~ S-08）

**方法：** 对每个状态各造一条任务；对表中 13 个动作逐个用**有权限的身份**调用（避免被 403 抢先）。表中「允许」的动作应成功并进入指定状态；其余所有动作必须返回 **409 INVALID\_STATE**，且任务状态不变、时间线无新增事件、`result` / 字段不被改动。`note` 在任何状态都允许。

| 编号 | 当前状态 | 允许（成功后的状态） | 必须 409 的动作 |
| --- | --- | --- | --- |
| S-01 | 待领取 | claim → 进行中；force\_close → 已关闭；note | complete、fail、timeout、extend、accept\_pass、accept\_fail、requeue、reassign、reopen、close |
| S-02 | 进行中 | complete → 待验收；fail → 未解决；timeout → 未解决（late，TEST\_MODE）；extend（仍进行中）；force\_close → 已关闭；note | claim、accept\_pass、accept\_fail、requeue、reassign、reopen、close |
| S-03 | 待验收 | accept\_pass → 验收成功；accept\_fail → 验收失败（+新一轮）或需人工处理（第 3 轮）；force\_close → 已关闭；note | claim、complete、fail、timeout、extend、requeue、reassign、reopen、close |
| S-04 | 验收成功 | 仅 note | 其余 12 个动作 |
| S-05 | 验收失败 | 仅 note | 其余 12 个动作 |
| S-06 | 未解决（含超时） | requeue → 待领取；reassign → 待领取；force\_close → 已关闭；note | claim、complete、fail、timeout、extend、accept\_pass、accept\_fail、reopen、close |
| S-07 | 需人工处理 | reassign → 待领取；reopen → 验收失败（+新任务）；close → 已关闭；note | claim、complete、fail、timeout、extend、accept\_pass、accept\_fail、requeue、force\_close |
| S-08 | 已关闭 | 仅 note | 其余 12 个动作 |

| S-A3 | 待验收 | `[accept_pass, accept_fail, force_close]` | 本项目验收 BOT（非执行者）：accept\_pass、accept\_fail、note；管理员：force\_close、note |

### 6.2 错误码检查顺序（A-06 / A-10 附加用例）

顺序固定：401 → 404 → 403 → 400 → 409。

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| S-X1 | 无令牌 / 无效令牌调任一接口（含 `/mcp`） | 401 UNAUTHENTICATED |

| S-X4 | 非管理员对待验收任务调 reopen | 403（先于 409） |

| S-X6 | 管理员对未解决任务 requeue 但缺 `why` | 400 |
| S-X7 | 错误响应格式 | 均为 `{error, message}`，`error` ∈ UNAUTHENTICATED / NOT\_FOUND / FORBIDDEN / BAD\_REQUEST / INVALID\_STATE / RATE\_LIMITED |
| S-X8 | 被拒绝的请求（403 / 409）后查看时间线 | 无新增事件；服务端日志有记录 |

## 7 动态流转验收（D-01 \~ D-20）

每条流程用独立任务，**逐步断言**状态、关键字段、时间线事件和统计卡数字。

| 编号 | 流程与步骤 | 关键检查点 |
| --- | --- | --- |
| D-01 | 验收 BOT 发布 → BOT 认领 → 提交完成 → 验收 BOT 通过 | 状态依次：待领取 → 进行中 → 待验收 → 验收成功；时间线 4 条事件（发布 / 认领 / 提交完成 / 验收），操作人正确；验收列「✔ 通过 · 第 1 轮结案」；统计卡每步同步 |
| D-02 | 第 1、2 轮验收失败，第 3 轮验收成功 | 第 1、2 轮结束后各生成新一轮（轮次 +1、待领取、沿用 assignee）；每轮 `summary` 为「自动汇总：原任务 + 上轮结果「…」+ 失败原因「…」」，引用的是上一轮的真实结果和原因；任务链 3 个节点；第 3 轮验收列「✔ 通过 · 第 3 轮结案」 |
| D-03 | 连续 3 轮验收失败 | 第 3 轮失败后原行转需人工处理，任务总数仍为 3 个，不再生成新任务；验收列含「已达 3 轮上限，等待管理员审批」 |
| D-04 | 进行中任务超过时限（TEST\_MODE 用 `deadline_seconds`） | 超时后自动转未解决；`late=true`；`done_at`=`deadline_at`；`result=超时未提交结果（系统自动转入）`；事件操作人「系统」；整行黄色，「超时」卡 +1，且计入「未解决」；**不打开页面、只调 GET** 也能触发惰性判定；Cron 每分钟兜底【正】 |
| D-05 | 未解决（BOT 报告失败，或超时）→ 管理员放回待领取（填原因）→ 原 BOT 重新认领完成 → 验收成功 | 放回后字段清空、`todo_at` 重置；重新认领时 `deadline_at` 重新计算；最终验收成功 |
| D-06 | 未解决 → 改派（轮换 / 指定，填原因）→ 新 BOT 完成 → 验收成功 | 两种改派方式各跑一次；改派后旧 BOT 认领 403；新 BOT 可认领；时间线有「旧 → 新」记录；详情「改派 N 次」递增 |
| D-07 | 需人工处理 → 再开一轮（轮次重置为 1）→ 再失败 3 轮 → 又回需人工处理 | 新任务第 1 / 3 轮；再失败 3 轮后再次需人工处理；任务链包含全部节点，且新任务在同一链 |
| D-08 | 需人工处理 → 关闭（填原因） | 已关闭；验收列「管理员已关闭」；终态后只能留言 |
| D-09 | 需人工处理 → 改派（轮次保持 3）→ 完成 → 验收失败 | 轮次仍为 3；验收失败后直接回到需人工处理，**不**生成新任务 |
| D-10 | 未解决 → 改派给另一 BOT → 另一 BOT 完成 → 验收失败（第 1 轮，未达上限） | 下一轮默认派给**当前**执行 BOT（沿用上轮 assignee，而不是最初的 BOT） |
| D-11 | 空输入默认值 | 完成摘要为空 → `已完成`；BOT 失败原因为空 → `未说明原因`；验收失败原因为空 → 400（前端不发请求） |
| D-12 | 超时转未解决后 BOT 再提交完成 / 失败；待领取任务放置很久 | 再提交一律 409；待领取任务无截止时间，放多久（含超过 24 小时）都不会自动转状态，只会变橙 |
| D-13 | 并发 | 同一任务 2 个并发认领只有 1 个成功；同一待验收任务 2 个并发验收失败只生成 **1 个**新任务，另一个 409；再重复校验任务总数 |
| D-14 | 强制关闭 | 待领取、进行中、待验收、未解决各自强制关闭成功（缺原因 400）；进行中被强制关闭后 BOT 再提交 409；终态和需人工处理强制关闭 409 |
| D-15 | 延期 | 进行中延期 30 / 60 / 120 分钟，截止时间相应后移，状态不变，超时判定按新截止时间；其他分钟数 400；非进行中 409；非管理员 403；可多次延期 |
| D-16 | 留言 | 8 种状态（含 3 种终态）均可留言；不改变状态、轮次、结果；空文本且无图 400；观察者和无关 BOT 403；留言出现在时间线并标明操作人 |
| D-17 | 图片全流程 | 发布附图 → 完成附图 → 验收失败附图 → 下一轮任务图片 = 原任务图片 + 验收失败图片；再开一轮的新任务带有原任务图片；每个事件的图片在时间线都能点开 |
| D-18 | 时限从认领起算 | 发布时 `deadline_at` 为空；任务放置较久后认领，`deadline_at` = 认领时刻 + 时限；放回待领取 / 改派后 `deadline_at` 清空，下次认领重新计时 |
| D-19 | 逾期与待我处理 | 待验收 > 24 小时、待领取（自 `todo_at` 起）> 24 小时 → `od=true` 整行橙色；放回待领取 / 改派后重新计时，不再橙；`mine` 按四种角色规则正确；标签页标题数量同步 |
| D-20 | 任务链 | 任一节点查询 `chain` 返回根任务及全部后代，按 id 升序；再开一轮产生的新任务也在同一链；详情「任务链」可点击跳转 |

### 10.3 Agent 完成定义（Definition of Done）

1. 先确认环境和身份可用：9 个 BOT、管理员、观察者令牌（或演示环境下拉）都能登录，`/api/me` 返回正确。
2. 按第 3 → 9 章顺序执行，每条用例记录 PASS / FAIL / BLOCKED 及证据。
3. 发现 FAIL 立即登记缺陷（第 12 章模板），继续执行其余用例。
4. 全部执行完后，按 10.2 核对覆盖，补齐遗漏。
5. 修复缺陷后回归：重跑相关编号 + S-01 \~ S-08 + D-01 \~ D-03 作为冒烟。
6. 输出验收报告：覆盖率、通过 / 失败 / 阻塞数量、缺陷清单、已知差异结论、最终结论（合格 / 不合格）。
7. 只有满足第 1 章 5 条通过标准，才能给出「合格」。
